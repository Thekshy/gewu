# 11 · 思考：长程任务的三层缺口与扩展路径（设计推演，未立项）

> 本篇与 [05](05-tool-scaling.md) 同体裁：设计推演而非现状描述。区别是锚点——

## 现状与它的天花板

长任务相关的能力，现在已经有：

| 能力 | 现状 | 承载 |
|---|---|---|
| 步骤知识 | 制度文本/办事指南进语料，检索即得 | rag 域 |
| 办理执行 | query_flows → run_flow 单入口，闸 O(1) | agenttools + 注册表 |
| 多步串联 | 单循环内 agent 自主多轮调工具 | create_agent |
| 中断恢复 | 回合边界 checkpoint，确认流可跨天 | [09](09-durable-execution.md) 第一档 |

天花板拿一个任务压出来就清楚了：「我要休学创业」。它要 查制度 → 解读条件 →
列材料清单 → 提交申请 → 等审批（数天）→ 后续节点（销假/复学）。现形态答得了
知识、办得了单步，但有三处会断：步骤知识若不在语料则答不全；跨 flow 的串联
靠主模型临场发挥，无人保证顺序与完整性；「我办到第几步了」没有任务级记忆。

## 诊断：三个正交缺口

1. **内容缺口**（知识在不在）：不在语料 → 补语料，零新机制。校内公开办事指南
   大多属此类——这也是「语料 + 单 flow」能覆盖目前大部分场景的原因；
2. **编排缺口**（多步怎么串）：下一步依赖上一步的结果。分两档——路径确定 →
   **复合 flow**；路径开放 → **skill 引导**；
3. **状态缺口**（跨会话跟到哪了）：任务天然横跨数天数会话，需要任务级生命周期。

主判据还是那句「Use the model for judgment, use a workflow for control」：
路径越确定，越下沉为 workflow；越开放，越交给 model 判断——skill 不是给系统
加控制流，是给模型的判断喂程序性知识。三个缺口是三件不同的事，先分清缺哪个，
再决定造哪个。

## 方案一：复合 flow（路径确定的长流程）

**形态**：注册表新增一类 meta 条目——steps 引用既有子 flow（如 查资格 →
提申请 → 登记备案），每个子 flow 过自己的闸（关键词/槽位/HITL 各自触发）。
agent 视角仍是**一次 run_flow 调用**：认知负担零增长，闸与回执语义原样保留，
这是该方案最大的优点。

**使用场景**：制度上规定死的串联流程——休学办理、毕业离校清单。特征：步骤
可枚举、顺序固定、每步输入输出明确。

**边界与风险**：read_only / 注册表双源陷阱在复合层级被放大（漏登一个子 flow
= 静默丢一道确认门），立项时注册表完整性必须配测试兜底。路径写死后开放性为
零：用户中途问「条件不满足怎么办」，它答不了，会退回 RAG 问答。

## 方案二：skill 引导层（路径开放的长任务）

**形态**：skills/ 目录，每个 skill 一份 markdown——何时用 / 前置条件 / 步骤
指引 / 失败绕行 / 退出条件。常驻上下文的只有清单（名字 + 一句话描述），命中
时全文注入 system prompt：渐进披露，与 [05](05-tool-scaling.md) 推演的③
（工具检索）同构，machinery 可复用 rag 域。

**关键立场：skill 是循环内的注入知识，不是外置编排器。** 不加路由层、不加
控制流——单循环主张（PARITY §0.9）不被稀释：run_flow 是 control 极，skill 是
judgment 极的支撑，两者换挡不替代。仓库里已有同构先例：deep_research 本质是
一个硬编码的 skill（「拆子问题→多路检索→聚合」的程序性打法固化成工具），
本方案是把它从代码泛化成数据。

**为什么组合必须留给 agent 自决**：用户任务是任意 flow 的复合，N 个流程的
组合空间（子集 × 顺序 × 中间条件分支）不可枚举——「先编排好」这条路在数学上
就接不完。可行的分工是把三层拆开：**决策在模型，安全在闸，知识在 skill**。
闸挂在动作级（角色 / 槽位 / HITL 确认），O(1) 且与调用顺序无关——agent 就算
决策出荒唐序列，最坏结果是用户收到一堆确认卡片后逐个拒绝，而不是系统执行了
荒唐序列。对比传统 workflow 校验**计划**（图先审后执行，每个新组合都要人
编排），动作级校验天然免疫组合爆炸——这也是 agent-first 的答辩护栏：**组合
不可枚举 ⇒ 编排必须内生在循环里，注册表收的是原子动作加闸，不收序列**。模型
缺的从来不是组合的能力（单循环今天就能连调多轮工具），是组合的知识——这
正是 skill 要补的那块。

**与「塞进 RAG」的分界**：RAG 检索的是陈述性知识（「制度是什么」，被**引用**
进答案），skill 注入的是程序性知识（「怎么操作」，被**遵循**成动作）。判别
问句：这段文字是被模型引用，还是被模型逐条执行？前者语料，后者 skill。

**使用场景**：跨 2-3 个 flow 且路径依赖中间发现的开放任务——「先查我的请假
余额，不够的话看能不能拆两次请」「比对我的课表和场馆余量，约一个不冲突的」。

**工程约束（诚实代价）**：skill 的效果上限 = 主模型的指令遵循能力（flash
无视否定指令的教训在长指令下放大）。铁律：**skill 只能提名路径，不能绕闸**——
一切写操作仍必须走 run_flow 的确认门，与三方接口接入「只能提名不能裁决」是
同一防御哲学。

**加载机制：开源界的收敛形态是「清单常驻 + 模型按需读」，不是确定性注入。**
两家源码实证：WeKnora 三级渐进披露（internal/agent/skills/skill.go:36-40）——
Level 1 元数据（名字+描述+`skill://` 路径）常驻 system prompt，Level 2 正文由
模型调 `read_file(skill://…)` 按需读，Level 3 附属文件再按需；read_file 校验
目标必须在 Level 1 清单内、拒绝路径穿越（tools/read_file.go:152-171）——
「只能读清单内的」就是提名约束。ZCode 同构：清单以 system-reminder 形式注入
对话头部并计入缓存前缀（整段 20K 字符预算，超限降级为仅名字+路径），全文由
模型调 Skill 工具懒加载（tools/handlers/skill.ts），另有硬门禁形态——危险
操作前强制「会话历史里必须有一次成功的 skill 加载」否则 428 拒绝
（workflow-skill-gate.ts:17-39）。**修正记要**：本篇初版曾倾向「确定性 top-k
注入」，那是在为 GLM 可靠性疑虑前置机制；开源界（跑在前沿模型上）的选择是
模型触发 + 关键点确定性守卫。gewu 折中：默认同构（清单常驻+模型按需读），
可靠性敏感场景点状兜底——借 WeKnora 的 must_use 强制注入（@skill 等价物）
或 ZCode 的已读门禁。另有一个免费杠杆：AGENT_SYSTEM 现在只交代单入口怎么选
（专属工具 vs query_flows→run_flow），没讲「复杂诉求可拆成多步逐个办理」——
一句 prompt 的事，不说模型可能一步完不成就直接甩给用户。

## 方案三：任务状态（跨会话的真长程）

**与 09 的分工**：[09](09-durable-execution.md) 讲「任务中断后怎么恢复」
（持久化边界切在哪），本节讲「任务天然横跨多会话时怎么管理生命周期」——
建在 09 第一档之上，不替代它。

**形态**：tasks 表（id / user / goal / status / checklist / updated_at）；
turn 开始时注入「进行中的任务及其进度」；followups 追问（P25）承担「回来
续办」的入口体验。

**开源界的轻量形态**：这一层在成熟项目里不是重任务系统，而是「模型维护的
todo 清单 + 节流提醒 + 持久化」。ZCode 的 TodoWrite 按会话落 SQLite、模型
每次全量替换、harness 以 ≥10 轮节流的 system-reminder 注入当前清单（持久化
为合成消息，冷恢复可重建）；plan 文件原子写盘、resume 时重注入引用
（todo.ts / plan-mode.ts / turn-loop.ts:138-156）。WeKnora 的 todo_write 更
克制：限检索/研究类步骤、同刻仅一个 in_progress（tools/todo_write.go:12-31）。
LangChain 开源的 deepagents 把同构三件套（write_todos + 文件系统 + 子代理）
做成最小脚手架。共同设计原则（ZCode 源码注释明说）：**以模型可见的消息
历史为唯一事实源**——不另立会话级状态集合，compaction/resume 后答案从历史
重建。gewu 若做，从 TodoWrite 形态起步而非 tasks 表。

**使用场景**：等待数日的审批流（请假 3 天以上学院批）+ 多步清单（办到第
2/5 步）。现状 leave_status 能答单笔查询，答不了「我接下来还要办什么」。

**边界**：毕设阶段不建议立项——没有真实用户就没有真实长程需求，属为架构
完整性造需求；论文里作 future work 一句话即可。

## 组合的执行：依赖、并行与速度

自决组合落地时绕不开三个执行层问题。开源项目的源码级答案相当收敛：
**依赖不用 DAG，判断在模型；并行读随意、写做屏障，安全在代码；速度靠并行
子代理与减轮次，不靠加速工具**。

**依赖：没有项目用 DAG**。WeKnora 全库 grep 证实 agent 层无 dag/depends_on
机制；ZCode 调度器按工具元数据分组，agent 同轮调用间不声明依赖（dependsOn
恒为空）。依赖的传递靠三类机制叠加：

1. **模型分轮表达**（主通道）：ReAct 轮次串行，B 发起时 A 的结果已在消息
   历史里——循环天然提供的管线；
2. **句柄系统**（数据依赖的机制化）：WeKnora modelcontext 把工具产出注册为
   cN/dN 请求局部句柄，模型在后续工具参数里引用，执行前解码，**未解析即
   fail-closed 拒执行**（internal/agent/act.go:574-578）——gewu 的回执单号
   （VE-0001）就是人工形态的同一机制；
3. **prompt 指令**：WeKnora 系统提示词明写「Batch independent reads; keep
   dependent operations in order」（internal/agent/prompts.go:278-280）。

**并行：读并行/写屏障，两个项目独立收敛到同一判据**。框架层早已并发：
LangGraph ToolNode 对同轮多条 tool_calls 走 gather/线程池，eino 的 ToolsNode
默认并行（[竞品报告](../research/agent-projects-report.md) eino 节）——
「要不要并行」一半不由我们决定，模型批了就并发。真正要设计的是写，两家
源码给出同构答案：

- WeKnora **执行屏障**：14 个内置只读工具白名单可并发；写操作/任意代码/
  未知及 MCP 工具一律屏障——排干在途读 → 同步执行写 → 再放后续读，全程
  保持模型原始顺序；errgroup 限流 8、单工具 panic 只失败自己；另有
  per-(会话,路径) 文件锁兜底读-改-写竞态，行为有专门测试锁定
  （act.go:308-315 / execution_policy.go:3-17 / act_order_test.go）。
- ZCode **元数据分级**：调度器拓扑分组、默认并发 10；`destructive` 或
  `concurrentSafe=false` 的工具进单元素组串行，全部写类工具显式标 false
  （scheduler.ts:85-103）；后台任务（run_in_background）经 RuntimeTaskRegistry
  在下一模型步以合成通知回流（turn-loop.ts:55-65）。

gewu 落地即此前推演的 write_tools() 屏障——现在不是猜想而是双项目实证的
成熟模式；且 gewu 的 HITL 确认门（写流程参数齐即中断整轮等人）比两家的
屏障更严，已天然覆盖其大部分语义。待验证项不变：GLM 是否真吐多条
tool_calls（trace 看单条 AI message 即知）。

**速度**。竞品报告里所有研究型 agent 的提速答案是**并行子代理**而非加速
工具：Onyx 每轮并行 ≤3 个 research_agent、ODR asyncio.gather ≤5（「收集
一批→gather→逐个包装回流」）、GPT Researcher 信号量分层并发、STORM persona
多路并行。对 gewu 这类单循环+本地毫秒级工具的形态，轮次才是成本大头
（P27 观测主模型占 84% 跨度），按性价比排：

1. **第一步就走对**：skill 的前置知识让任务不绕路，省下的是整轮的试错；
2. **批量读**：模型一轮吐多条独立读，N 轮变 1 轮，省 N-1 次主模型调用；
3. 小模型分流已就位（planner / classify 走 small=True）；
4. STREAM_ANSWER 管感知延迟（已在）；
5. deep_research 子问题检索串行——60 块语料不值得动；接外部慢 IO（三方
   接口）时先抄 ODR 的 gather≤5 模式。

## 三方案对照与立项门禁

| 维度 | 复合 flow | skill 引导 | 任务状态 |
|---|---|---|---|
| 解决缺口 | 编排（确定路径） | 编排（开放路径） | 状态 |
| 控制权在 | 代码 | 模型（闸兜底） | —（与两者正交） |
| 新增机制 | 注册表组合关系 | skills 目录 + 注入 | tasks 表 + 生命周期 |
| agent 认知负担 | 零 | + 清单 | + 进行中任务提示 |
| 主要风险 | 双源陷阱放大 | 指令遵循上限 | 需求真实性 |

三者不互斥：skill 引导 + 关键步骤沉 flow 是自然组合（开放路径上的确定性写点）。

立项前按「复杂度用评测买」先走一步：构造复合场景样板（如休学创业全流程）
在**无任何引导**下真跑，记录失败模式——检索不到 → 补语料；不会拆步/顺序乱 →
skill；丢进度 → 任务状态。失败模式决定造哪层，别先造层再找用途。评测口径
可顺手抄 ODR 一件：**编排行为精确断言**（首条消息 tool_calls 数、事件序列
== 参考值）——执行形态本身进考卷。

## 边界与已知短板

- 全篇未立项，锚定 2026-10（P37 后）形态；实现细节以立项任务书为准。
- 「内容缺口已覆盖」是经验判断，依赖语料盘点成立——新办事指南上线时先问
  语料有没有，再问要不要新机制。
- skill 层的评测口径未定：引导前后任务完成率对比是自然起点，但前提是先有
  可断言终态的复合用例（可在既有交易型评测上扩一档）。
- GLM 是否一次吐多条 tool_calls 未实测（trace 一看即知）；写屏障模式在
  WeKnora/ZCode 已实证，gewu 落地为 write_tools() 屏障，未实现待立项。
- WeKnora/ZCode 跑在前沿模型上——「模型触发加载 + 点状确定性守卫」在 GLM
  档模型上的实际可靠度，是本篇最大的未验证假设。
