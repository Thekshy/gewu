# 08 · 存储选型：git、数据库与内存的边界

> 回答「上下文的每一层用什么存」。先给总规则，再逐层落地，最后修正一个常见推理：
> 「要高可用所以全上数据库」——数据库给的是持久性，把最稳定的内容放进最重的
> 依赖里，可用性反而变差。

## 总规则：选存储看「谁写、怎么读」

| 真相源 | 适用内容 | 为什么 |
|---|---|---|
| **git（代码/文件）** | 人写的、要 review 的、随产品复杂度演进 | diff / 回滚 / 可测试 / 零运行时依赖 |
| **数据库** | 机器写的、要按 key 或语义查询的、随用量增长 | 索引 / 向量 / 事务 / 水平扩展 |
| **内存 + 边界落盘** | 易变热态、单回合生命周期 | 快；只在需要跨边界存活时外置 |

判断口径：**用量增长的数据（用户 × 会话 × 记忆条数）→ 数据库；随产品复杂度增长的
数据（提示词、工具定义）→ git**。两条增长曲线不同，不该共用一种存储。

## 逐层选型

### 稳定层（system prompt / 工具清单）→ git，不是数据库

提示词是仓库里的版本化文件或代码常量；静态工具的定义跟着工具代码走（可执行体本来
就在代码里，注册表只是元数据）。理由：

1. 这层内容的变更要走 review 与灰度——git 天然给 diff/审查/回滚，DB 里的 prompt
   改动反而绕过代码审查；
2. **零运行时依赖**：DB 是一个故障域，DB 挂了服务连最稳定的内容都加载不出来——
   把系统最大的确定性押在最大的依赖上是可用性反模式。

何时才进库：多租户 SaaS 各租户不同 prompt/工具集——形态也是「代码放默认值，
DB/配置中心放覆盖值」；动态注册的工具（MCP 外部服务运行时挂载）才需要注册中心。
Langfuse 这类提示词管理平台看着像「prompt 进 DB」，核心价值是版本管理 + 灰度标签
——本质是「给 prompt 造的 git」，DB 只是实现载体。

### 长期语义记忆 → 数据库 + 向量索引

**表结构：一行 = 一条记忆条目，embedding 是写时算出的冗余列**。pgvector 概念形状：

```sql
CREATE TABLE memories (
    id          BIGINT PRIMARY KEY,
    user_id     TEXT NOT NULL,              -- namespace：多租户隔离的硬边界
    content     TEXT NOT NULL,              -- 真相本体："用户是大三学生，绩点 3.2"
    kind        TEXT,                       -- 事实类型：profile / preference / fact
    key         TEXT,                       -- 结构化键：grade / gpa（UPSERT 冲突键）
    embedding   vector(1024),               -- content 的向量，写时计算
    status      TEXT DEFAULT 'active',      -- active / superseded（软失效，不物理删）
    created_at  TIMESTAMPTZ,
    updated_at  TIMESTAMPTZ
);
```

三个设计要点：

1. **文本是真相，向量是索引**——embedding 丢了可全量重算，原文丢了不可逆；
2. **软失效代替删除**——「我大四了」不覆盖旧行，而是旧行标 superseded 指向新行；
   直接 UPDATE 丢历史，无法审计抽取错误、无法回答「上学期他说过什么」；
3. **namespace 过滤是查询必选项**，不是优化项——跨用户记忆泄漏是这层的头号安全事故。

**写路径**（回合结束异步）：

```
本轮对话 → LLM 抽取候选事实 → embed
        → 与该 user 现有记忆相似度比对（ANN 召回 top 几条）
        → LLM 决策操作：ADD / UPDATE / DELETE / NOOP
        → 落库（插入新行 / 旧行软失效）
```

冲突检测这一步是 mem0 与「朴素每轮往库里塞」的区别——没有它，同一事实会有多个
略有差异的版本，读时全被召回、互相污染上下文。

**读路径**（回合开始）：

```
补全后的问题 → embed → ANN top-k（user_id + status=active 过滤）
            → 时间衰减加权 → 截断到记忆 token 预算 → 拼进"已知用户信息"块
```

读取分两种：**核心画像整块加载**（量小，几十条，不需要检索）；**长尾记忆按相关性
向量召回**（量大后才需要）。量再大时上混合检索（BM25 over 记忆文本 + 向量）——
记忆检索与知识库检索是同一套 machinery，可复用。

### 短期情景记忆 → DB 事件日志为真相源 + 缓存热读

- **append-only 事件/消息表**（session_id + 序号）：天然支持审计 / 回放 / 恢复
  ——事件溯源在 agent 会话上的应用；
- **热路径缓存**（进程内或 Redis）：最近 N 轮原文；
- 拼装是**查询**不是存储：取「最近 K 条原文 + 更早的摘要」，摘要本身也是机器写的、
  也要落库；
- append-only 天然幂等，失败重试与重放安全。

### 工作记忆 → 按生命周期切

单回合内的状态（本轮 plan、临时 TODO）留进程内存——回合失败整轮重来，不需要持久化；
跨回合的任务状态才外置（Redis TTL 贴合过期语义 / DB JSONB 支撑跨重启续办）。plan
甚至可以直接建模为对话上下文里的结构化块，不设独立存储。展开见 [09](09-durable-execution.md)。

## 高可用论证的修正

「失败可重试、保证稳定 → 数据库」缺了一环：数据库给**持久性**，高可用还需要
**无状态计算 + 幂等写入 + 状态可从持久日志重建**。只把状态搬进 DB，实例仍绑着连接，
故障切换照样难；反过来「append-only 日志 + 无状态服务 + 可重建」才是会话类系统的
高可用配方。另外，稳定层放代码本身就是 HA 措施——DB 全挂的场景下，系统最核心的
行为定义还在。

## 格物映射

| 层 | 格物实现 | 规则对应 |
|---|---|---|
| 稳定层 | 提示词代码常量（prompts.go / routing/prompts.go） | 人写 → git |
| 长期语义 | memory.db facts 表（UPSERT） | 机器写 → DB |
| 短期情景 | memory.db episodic（追加式） | append-only DB |
| 工作记忆 | sessions.db TxSession（跨重启续办）/ 内存 map 可选 | 跨边界才外置 |

P8 退役微服务时的一个决策佐证：唯一被「吸收」进单体的能力是会话持久化——因为只有
它真的需要跨进程存活。四库分离让每个关注点独立演进：哪个先撑不住，哪个先换 PG，
接口不变。
