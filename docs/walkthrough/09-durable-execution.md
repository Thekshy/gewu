# 09 · 任务中断与恢复：从回合边界到任务连接解耦

> 问题：web 平台上，用户任务跑到一半暂停/退出怎么办。先纠正一个前提——
> 「工作记忆用内存不持久化」只对**单回合内**的状态成立；真正的问题是持久化边界
> 切在哪。业界按任务要活多久分三档，由轻到重。

## 第一档：回合边界 checkpoint（格物现状）

回合结束把任务状态（槽位 / 阶段 / plan）落到 DB，下一轮进来先查有没有进行中的任务。

- 用户「暂停退出」在这一档的定义：**任务停在等用户输入的暂停点上退出**（追问槽位、
  等确认）——这些点天然是安全的持久化边界；
- 确认流就是一个可以持续数天的人机暂停：状态在库里，不依赖任何进程活着；
- **格物实证（P8-1）**：TxSession 落 SQLite——「帮我预约羽毛球馆」问到槽位 →
  kill 服务 → 重启 → 同 session_id 发「明天晚上七点」继续走到确认。跨重启续办
  是被评测验证过的行为。

## 第二档：步进 journal（事件溯源）

任务要在**非暂停点**也能恢复（ReAct 跑到第 5 轮、第 3 个工具刚执行完），就把每一步
落成 append-only 事件（step/start、tool_call、tool_result…），恢复 = 重放事件重建状态。

- 对应 DeepSeek Harness 的 interrupted 语义：进程崩溃后，恢复层发现日志里有未闭合的
  turn，用 interrupted 闭合它，**由人决定是否续**；
- 工程化产品：Temporal / Restate（durable execution：每步自动 checkpoint，恢复自动
  replay）、LangGraph checkpointer（每个 super-step 后把 state 快照写 DB/Redis）；
- 两条铁律：
  1. **重放必须幂等**——工具调用带幂等键 / 请求 id，恢复重放不能把预约下两次；
  2. **恢复后默认不自动续行**——Harness 的 Goal activation 恢复后是 disarmed、要人
     重新授权（fail-closed，防止服务重启让一批历史任务集体复活烧钱）。

## 第三档：任务与连接解耦（web 平台的成熟终态）

前两档没有挑战一个共同前提：任务和 HTTP 连接绑在一起。ChatGPT 模式把它们拆开：

- **任务是服务端后台任务，事件流持久化，SSE/WebSocket 只是「观看进度的视图」**；
- 关掉标签页任务照跑；回来重连就重读事件流接着看——断线重连不是「恢复任务」，
  而是「重新订阅」。

这才是「用户中途退出」的完整答案：退出只是断开了视图，任务本身在后台 + 事件日志里活着。

## 格物的取舍与升级判据

| 档位 | 格物现状 | 升级信号 |
|---|---|---|
| 一：回合边界 | ✅ 已做（sessions.db） | — |
| 二：步进 journal | ❌ 回合内「连接死任务死」（ctx 取消传播） | 单回合步骤变贵（长 ReAct / 深研多路检索）、或产品要求非暂停点可恢复 |
| 三：连接解耦 | ❌ SSE 同步直连 | 多实例部署、长任务、要求「关页不丢进度」 |

「连接死任务死」是**刻意的成本选择**：回合级重试很便宜（用户重发一次问题），
为它上 journal 不值——这是「什么规模换什么方案」的又一次应用。P10 的 done.reason
（aborted 可观测）正好是升级前的观测铺垫：先能统计有多少回合死于断连，
才知道升级二档的收益有多大。
