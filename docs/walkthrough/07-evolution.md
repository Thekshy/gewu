# 07 · 演进史：三个形态与两次收口

> 格物经历过 Python 单体 → Go 单体 → 六微服务 → 模块化单体三个形态、两次主动收口。
> 每一步的判据比结果更值得记录：**形态是学习目标不是交付目标**，切换的底气来自
> 等价证明。

## 时间线

```
Python v1（FastAPI）        产品形态验证：路由/检索/办理/评测全绿
   │ 行为冻结：PARITY.md 成为唯一规格
   ▼
Go 单体重写                 clean-room 对照，26/26 逐题等价，修掉 8 个原设计缺陷
   │ （go-notes §10）
   ▼
六微服务（P0~P5）           拆分边界/存储/MQ/重试降级等 8 个 ADR，逐题 PARITY 26/26
   │ 学习目标达成（拆过、对过、痛过）
   ▼
退役收口（P8）              先吸收会话持久化（微服务独有的能力缺口）→ 再删源
   │                        -16k 行，gRPC/Redis/网关依赖全消失
   ▼
拆包收口（P9）              HTTP 层独立 internal/api，路由域独立 internal/agent/routing
                            lint-arch 固化七条依赖规则
```

## 每一步的判据

**Python → Go（为什么重写）**：未上线无历史包袱，重写本身就是验证——SSE 每连接一
goroutine 的取消传播（断开即刻停止烧 token）、BM25/RRF/事件键序的构造性确定、
单二进制冷启动 ~50ms。以 PARITY.md 为规格做 clean-room 对照，重写过程反而修掉了
原设计 8 个缺陷。

**单体 → 微服务（为什么拆）**：学习目标——拆分边界（ADR-0001）、存储选型与降级
（0002/0008）、MQ 解耦的代价（0003）、重试与降级（0004）、业务归属（0006）、分布式
预算计量（0007）。每个决策单独成 ADR，逐题等价证明拆分没有引入行为漂移。

**微服务 → 模块化单体（为什么删）**：双形态只剩维护成本没有收益。删除遵循
「先吸收、后删除」——微服务里单体没有的能力（办理会话跨重启续办）先搬进单体并过
评测，再删源。退役不是丢弃学习成果：代码在 git、决策在 ADR、等价证据在
docs/history/ 与 tag `pre-ms-removal`。

**拆包收口（为什么是 api/routing 而不是更多）**：只拆接缝真实的——路由只依赖 LLM
的 Chat 能力，天然自成一体；react/transaction 与 Deps/TxSession/emitFn 耦合深，
强行拆包只会造出假边界。依赖规则交给 lint-arch 守护，靠工具不靠自觉。

## 两条经验

1. **等价证明让切换有底气**：每次形态切换前先冻结行为规格（PARITY.md），同数据集
   逐题对照。没有这个，重写/拆分/合并都退化成「感觉没问题」；
2. **收口比扩张更难也更重要**：知道什么时候删（微服务退役）与知道什么时候拆
   （P9 拆包判据）是同一种能力的一体两面——都以「这个边界是否真实存在」为准。
